Where this sits

A story in a kstrl PRD is done when its passes flag is true. Today the only thing that ever sets that flag is the engineer agent, the same agent that wrote the code. Phase 1 then reads the flag back and fails the component if any story is still false. Nothing in kstrl/ writes it. measured There are six occurrences of .passes in the package and every one is a read, a validation, or the serialiser.

That is one defect. The design says it is also a symptom, and the symptom is the interesting part. kstrl is described everywhere as a pipeline of phases, and a pipeline has no word for the rule that the thing measuring must not be the thing acting. So the defect had nowhere to be seen from. The document supplies a frame in which it is the first thing you see, then files a plan of thirteen issues in that frame.

The pull request itself changes no behaviour. So everything from the vocabulary table onward describes kstrl as the plan leaves it, and each claim carries a mark saying whether I checked it against the code on 72404e9, or reasoned it from the issue text, or could not check at all.

Start with a room

You want the room at 20 degrees. A thermometer says it is 17. The gap of three is the only number anything acts on. A box decides what to do about the gap and turns the boiler on. Someone opens a window, which the box did not command and cannot prevent.

Now the names, one each. The 20 is the set point. The thermometer is the sensor. The gap is the error. The box is the controller, and the boiler is the actuator. The window is a disturbance.

One property makes this a loop rather than a script: the sensor is independent of the actuator. Suppose the boiler could report the temperature. It would report 20, always, because 20 is what it was asked for. The loop would be perfectly stable and the room would be freezing. In kstrl the boiler is the engineer agent, and passes: true is the temperature it reports.

Why it was built this way

Why is a hand-run sensor the first item, ahead of the headline defect?

Every threshold in kstrl is a placeholder. The autonomy module says so in its own docstring. measured autonomy.py:38 reads "Every threshold in this module is an UNMEASURED PLACEHOLDER". The design's diagnosis of why is short: you cannot cheaply measure a sensor you cannot run. Press the button and count.

So ks sense (#222) wraps run_mechanical_verification, which already takes a path and returns a VerificationResult. The issue changes one signature, prd_path: Path | None, skips the two PRD-dependent checks when it is absent, and adds a command with a --json form. It writes nothing. The dampener (#227) is the same command pointed at a baseline, and the inner-loop sensor (#233) is the same function called between iterations, which is why the design calls this the item that makes the others cheap.

The dead end. An earlier draft of the same document had a section 7 that gated seven mechanisms behind "measure this number first": how often the reviewer disagrees with the done flag, how much stale text attempt 3 carries, review throughput to set a WIP bound, and four more. The draft that merged calls that wrong in its own section 5.0, and the evidence that killed it is the button above. Every one of those measurements needed a factory run to collect, so measure-first delayed both the value and the data. measured The only caller of the sensor is pipeline.py:2201. kstrl built the orchestrator first, and the components are now reachable only through it.

Why must the reviewer confirm the engineer's passes: true?

Phase 1 runs check_prd_stories first in its chain. It re-reads the PRD the agent just wrote and fails if any story is still false. measured verify.py:526 and verify.py:1398. Phase 2's reviewer already emits a verdict per acceptance criterion, and already computes which stories it covered. measured review.py:65 and review.py:547. The second sensor exists and is not consulted. Set the two sensors against each other below.

Two things about the end state are easy to miss. First, check_prd_stories stays. It still catches an agent that emitted COMPLETE with a story left false; what changes is that the flag stops being the sole authority. Second, in blocking mode the harness itself becomes the first writer of passes in kstrl's history: it reverts the story to false, appends a notes line beginning "reverted by reviewer", and saves the PRD, so the engineer's own step 7 ("pick the highest priority story where passes is false") picks the story up again. reasoned From issue #224 section 5; no code exists yet.

The dead end. The earlier draft put this fix near the bottom of the list, because it believed the engineer prompt's step 14 would become misleading and so the change crossed the H3 boundary: version bump, hash update, calibration re-run and human review in one PR. The merged draft re-read step 14. measured init_cmd.py:81 says "set that story's passes to true", and that instruction stays exactly correct under the new rule. The flag was always a claim; the harness just starts treating it as one. Removing the supposed prompt cost moved the item from expensive-and-important to cheap-and-important, and from fourth to third in the order.

The evidence that it costs something is the one part I cannot confirm. unconfirmed The design counts review:prd_criterion as the most frequent failure signature in this repository's journal, five of seventeen, across five runs on one trivial project. The journal is gitignored and not in the tree I was given. The design itself calls the number a hint rather than a rate.

Why does attempt 3's prompt list only what is failing now?

The retry context is four lists whose only mutators append. measured context.py:33 to :45; there is no clear, dedup or expiry anywhere in the file. It is serialised on retry and appended to at nine call sites, and its renderer ends with the line "Fix ALL issues listed above before completing." So on attempt 3 the agent is handed attempt 1's failures, which it may have fixed on attempt 2, unmarked, with an instruction to fix them all. That is windup. Choose where each attempt failed and watch the buckets.

The dead end. The obvious fix is to clear the context at the start of every attempt, which the manifest already does for a sibling field. measured pipeline.py:1035 sets comp.review_findings = "" in begin_attempt. Clearing throws away the entries whose sensors did not run in the latest attempt: an attempt that dies in verification never reaches review, so last attempt's review findings are neither fixed nor refuted. The rank rule exists to keep exactly those, and it is what the second "try this" move shows.

Running the rule outside the page turned up a seam. Issue #223 says a legacy entry loaded from today's JSON, tagged attempt 0, "always renders under Not re-measured". The rank rule as written puts such an entry under resolved whenever the later failure ranks at or above the entry's phase; my sweep hit that in three of five cases. measured docs/lessons/verify/pr-221/retry_context_rank.py. Whoever builds #223 needs a special case for attempt 0, and the issue's test 6 will fail without it.

Why does every new gate ship advisory, and who is allowed to make it block?

kstrl already has a doctrine for this and wrote it down once. measured findings.py:178: an adequacy finding defaults to advisory because "a gate that blocks on an invented number teaches people to switch gates off". The design applies that tier to every gate it adds instead of ad hoc. The rule for who may tighten a gate is already in the code too, at adequacy.py:721, and #224 copies it for the set-point gate. Drag the ladder.

What graduation requires is stated once so that it is not improvised later: the operator has seen the gate's output on real runs and can name what it caught and what it flagged wrongly. That is a judgement and it is deliberately the operator's. No issue in the milestone encodes a number in its place. The honest cost, which the design names, is that an advisory finding nobody reads manufactures the appearance of a gate; the antidote is that advisory output lands in the same Finding stream as phase_skipped, on the PR body and in the journal, so it is at least seen where the other findings are seen.

The dead end. Measure first. It sounds like the epistemology rule in this repository's own instructions, and the earlier draft followed it into seven blocked items. The trap is that "measure before building" and "never invent a number" are different rules. The second one survives: no threshold is chosen to make a feature shippable. The first one died, because a gate in advisory mode produces the measurement as a byproduct of running, and a gate that waits for the measurement produces nothing. judgement Whether "the operator can name what it caught" is a strong enough graduation test is the one place I would push back; it is the operator's call by design, and on a one-operator tool that is defensible.

Why does the daemon stop at one open pull request, and why is ks factory exempt?

Nothing bounds pull requests in flight. measured Grepping kstrl/ for max_open, open_prs, wip_, work_in_progress and concurrent_pr returns nothing. The bounds that exist are max_parallel = 4, one queue item per daemon cycle, and an inbox cap of 50, and none of them is about output. A loop that runs daily can open several unreviewed pull requests in a week, and then the reviewer is the thing that saturates. Sweep the gate.

The dead end. The earlier draft wanted a month of review-throughput data before choosing the bound. The merged draft ships it at 1 and calls the earlier caution over-cautious for a value that is one line of config, reversible in seconds, and carries a default from a team running the same bound in production. unconfirmed That last clause is the design's claim about its source; the source is not named on main and I did not check it. The second dead end is the one the widget's last move shows: treating a failed count as zero. The issue writes the opposite into the docstring, and the daemon waits.

Why halt when the review budget runs out, instead of merging on the cheap checks?

Today the pipeline already holds both answers. measured In hard mode with an unchunked review and max_adversarial_calls exhausted, pipeline.py:2465 to :2478 downgrades the review to SKIP, warns, and lets the component proceed on mechanical checks alone. A few lines later, :2479 to :2500, the chunked path refuses with an infrastructure_error finding. Same budget, same mode, two verdicts. Run components through the cap.

The dead end. Keep the downgrade because it is loud. It is loud: the warning prints and phase_skipped is recorded, so len(findings) == 0 still means every phase ran. The design accepts both qualifications and still calls this a priority inversion, because under budget pressure the harness sheds the sensor that does most of the catching. unconfirmed "Most" rests on the journal count, fourteen of seventeen signatures from the reviewer, which I could not open. What I can confirm is the shape: the chunked path already fails closed, so #226 makes the unchunked path match it and leaves advisory mode alone. The changelog entry is to be marked breaking for anyone who set a cap and relied on merges past it.

What this change deletes

In code, nothing; the PR is a document. In the document's own terms it deletes three things. It deletes measure-first as a gate, replacing seven measurement prerequisites with advisory mechanisms that produce the measurement by running. It deletes, by way of #223, the line "Fix ALL issues listed above before completing", which is the sentence that turns accumulated history into an instruction. And it deletes the assumption that fixing the done flag needs a prompt edit, which is what made the fix look expensive. The last commit also deleted a hundred lines of the document itself, and the tracker went with them.

What would make it wrong

Commit to an answer before you press reveal. Nothing here is recorded.

  1. #224 has landed with its default configuration and the autonomy ladder off. The engineer marked story B passes: true and the reviewer did not cover story B. What happens to the component?

    b. Advisory is the default and level 0 means the ladder is off, so the gate records only. Reverting the flag happens only in blocking mode, and blocking mode also retries. If you chose a, you have the graduated behaviour, which is the operator's decision to switch on, not the default.

  2. Attempt 1 failed review on criterion X. Attempt 2 failed verification on a typecheck error. What does attempt 3's prompt say about criterion X?

    b. Review ranks 2 and verification ranks 1. Attempt 2 stopped at verification, so review never ran, so criterion X has no fresh reading. The prompt renders it in full under a heading that says so and tells the agent to re-check it rather than assume it still applies.

  3. The daemon's max_open_prs is 1 and the gh pr list call fails with a network error. Does the daemon admit the next queue item?

    c. An unknown number of open pull requests is not zero, so admission is refused, and because nothing is known to be wrong with the queue, the refusal is a wait with an empty pause reason. The poison breaker is the gate that pauses; this one never does.

  4. Which R10 item requires a prompt version bump, a snapshot hash update and a calibration re-run under H3?

    c. H3 gates edits to a prompt body. Injecting a file into the prefix edits no body, and #224 reads a verdict the reviewer already emits. The design still recommends running calibration after #224 lands, because a new blocking condition near the reviewer is worth checking against the fixtures, but H2 does not demand it.

  5. The plan's own weakest point: which single fact, if it stays true on real projects, makes #233 a waste of a build?

    b. The inner-loop sensor instruments a loop that, on the five recorded runs, has iterated exactly once every time (unconfirmed here; the run data is gitignored). That is why #233 carries an entry criterion instead of an order number: a majority of the last ten runs above 1.00 iterations, across at least two projects. Build it before that and you are building for a problem that cannot be shown to exist.

One more thing would make the whole design wrong rather than one item: if the reviewer's per-criterion verdicts are noisy, requiring agreement amplifies the noise into retries. The check for that already exists and is the calibration suite, which is why the design asks for a calibration run after #224 even though no rule demands it. judgement I would treat that run as part of #224's acceptance rather than a courtesy.

kstrl began as a bare loop that re-ran a prompt until a condition held. It has spent its whole R-series moving away from that starting point, adding sensors, gates, envelopes, budgets and an autonomy ladder, without a word for what it was moving toward. This document supplies the word. Most of the work was already done.

That is the design's closing note, and after reading the thirteen issues against the code I think it is accurate. The frame is mostly a name for what the R-series already built. The three defects it makes visible were there all along.
